# Automated RLS Policy Testing in CI/CD

## Recommended architecture

Use a disposable local Supabase stack inside GitHub Actions for every pull request that changes database migrations, RLS tests, or the database client contract. The job should start a fresh Postgres/Auth/API stack, apply every migration from zero, run the Supabase database linter, create isolated test users through the local service-role API, and exercise the database through ordinary anonymous-key clients authenticated as customer and vendor users.

This approach tests the real boundary that production clients use: PostgREST, Auth sessions, RLS evaluation, database grants, triggers, and security-definer functions. It does not use the service-role client for assertions, because service-role access bypasses RLS and would make the tests meaningless.

| Approach | Tradeoffs | Cost | Setup complexity |
|---|---|---:|---:|
| Disposable local Supabase in GitHub Actions | Highest fidelity without touching shared environments; requires Docker startup time and a maintained test harness. | GitHub Actions minutes only | Moderate |
| Migration lint plus SQL-text checks only | Fast and cheap; catches policy drift and unsafe function settings but cannot prove behavior under authenticated sessions. | Very low | Low |
| Dedicated remote staging project per branch | Closest to hosted production behavior; requires project lifecycle, secrets, cleanup, and isolation management. | Supabase usage plus CI minutes | High |

The repository now contains the first approach, with the second approach included through `supabase db lint --local` and static migration checks. A remote staging project should be added only if production-specific extensions, storage behavior, or hosted configuration cannot be reproduced locally.

## Files added or changed

| File | Purpose |
|---|---|
| `scripts/test-rls.mjs` | Creates temporary customer/vendor users, signs in with the public anonymous key, and tests direct writes, trusted order creation, vendor status changes, vendor tampering, and invalid transitions. |
| `.github/workflows/rls-security.yml` | Reusable pull-request and deployment security workflow that starts Supabase, resets migrations, lints the database, and runs the test script. |
| `.github/workflows/deploy.yml` | Calls the reusable security workflow and makes the Pages deployment depend on its success. |
| `package.json` | Adds `npm run test:rls`. |
| `supabase/config.toml` | Local Supabase CLI configuration generated for reproducible startup. |

## CI execution sequence

The workflow performs these steps in order:

1. It checks out the commit and installs a pinned Supabase CLI version.
2. It starts a disposable local Supabase stack on the GitHub-hosted runner.
3. It exports only the local API URL, anonymous key, and locally generated service-role key into the current job environment. No production credentials are used.
4. It runs `supabase db reset --local`, which rebuilds the database from the repository’s migrations.
5. It runs `supabase db lint --local` to catch unsafe security-definer settings and other database warnings.
6. It runs `npm run test:rls`, which uses anonymous-key clients authenticated as temporary customer and vendor accounts.
7. It always stops the local stack, including when a test fails.
8. The production deployment job waits on the reusable RLS job through `needs: rls-security`.

## Security assertions covered

The current test suite verifies that a customer cannot directly insert an order, update protected order totals, delete an order, insert an arbitrary order item, update an existing order item, or delete an order item. It also verifies that the customer can create an order through the trusted RPC.

The vendor assertions verify that a vendor can perform an operational status update but cannot modify order totals or ownership and cannot perform an invalid backward status transition. The test creates the vendor role explicitly in `user_roles`, so it also verifies the canonical role model used by the RLS policies.

For each new sensitive table or RPC, add tests in the same pattern:

| Actor | Allowed case | Denied case |
|---|---|---|
| Anonymous | Public menu read, if intended | Any private table read or mutation |
| Customer A | Own order read and trusted order creation | Customer B data, direct order/item writes, protected field edits |
| Customer B | Own address and order access | Customer A data and cross-user address/order IDs |
| Vendor | All intended operational order/menu actions | Ownership, pricing, audit, and privilege changes |
| Service role | Controlled fixture setup and cleanup only | Never use it as the actor under test |

## Important implementation rules

Never point this workflow at production and never store a production service-role key in pull-request secrets. The service-role key used by the test script is generated by the disposable local stack and exists only for fixture setup and cleanup. The assertions themselves use the anonymous key plus normal Auth sessions.

Use unique, random email addresses and dish/order identifiers for every run. The test script deletes its temporary users and data in a `finally` block, but the disposable database is still the primary cleanup boundary. Do not use real customer data in fixtures.

Run the workflow for pull requests that touch migrations, security scripts, package metadata, or the workflow itself. On the default branch, make the deployment job depend on the reusable security workflow. Branch protection should require the RLS check before merge, and the deployment environment should require the same check before release.

## Local developer command

After Docker and the Supabase CLI are installed, a developer can run the same suite locally:

```bash
supabase start
source <(supabase status -o env)
export API_URL ANON_KEY SERVICE_ROLE_KEY
supabase db reset --local
supabase db lint --local
npm run test:rls
supabase stop --no-backup
```

## Limitations and next steps

The suite is behaviorally strong for RLS and database functions, but it cannot validate hosted project settings, production extensions, CDN behavior, or external authentication providers. Add a scheduled staging smoke test if those differences are material. The current repository’s existing lint warnings are unrelated to RLS and should be tracked separately so they do not obscure database security failures.

After merging, configure branch protection to require the RLS workflow and verify the live policy set once with a privileged SQL query against `pg_policies`. The live check is complementary: CI proves the migration behavior, while the live query proves that production actually applied every migration.
